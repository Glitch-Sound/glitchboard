# ポイント表示の可読性の報告

## 変更と根拠

ポイントの段階色をそのまま文字と半透明背景へ使い、完了時に透過する表示を修正した。\
通常の文字と同じように完了後の数値も読めることを優先し、色分け、完了状態と編集可否を維持した。

- 文字は段階色25%とテーマ前景75%、背景は段階色10%と editor 背景90%を使う。
- 一覧と詳細のバッジ、数値の選択肢は不透明な背景と共通の色を使い、選択行や Project 色の影響を受けない。
- 完了ポイントの opacity を1とし、一覧のチェックと名前の取り消し線、一覧と詳細の点線枠と操作不可で状態を区別する。
- 段階色の係数は style.css の共通規則だけに置き、YAML、UUID、ポイント値、集計と完了日の操作モデルは変更していない。

通常文字の4.5:1という判定は [W3C の Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)を参照した。\
今回は操作不可の完了ポイントにも同じ基準を採用し、画面全体への適合認証とは区別している。

## 実描画と測定

Chromium 156 の1440x1100の実ビルド画面を、一時 YAML と実 BoardSession で操作した。\
VS Code API と通信だけをアダプターへ置き換え、標準の前景と背景をダーク #d4d4d4 / #181818、ライト #333333 / #ffffff とした。\
オレンジと赤紫はテーマ変数を省略し、問題があった既定色を使う条件で検証した。\
他の色と検証条件は scripts/verify-point-contrast.mjs に記録している。

実 Chromium の算出色を canvas で数値化し、対象から html までの背景と group opacity を合成して文字と背景の相対輝度を比較した。\
合否は丸める前の比率で判断し、文字の縁のアンチエイリアスによる画素差とは区別する。\
全7値と未見積を通常と完了、一覧と詳細で確認し、選択肢と現在値、選択中の行、白と黒の Project 色、白と黒と灰色のチャート色も独立して確認した。

両テーマの計152測定すべてが4.5:1以上となり、完了ポイントの透過と点線枠も照合した。\
改善前の検査ではコントラスト不足120件と完了枠の不一致32件を検出し、通常と完了の透過問題を実装前に失敗で確認した。\
完了解除後の編集と既存の保存動作は改善前から成功しており、今回も維持した。\
選択中の行の追加測定も、既に共通の不透明背景が適用されたため最初から成功した。\
配色変更だけの時点で Event 以下の保存データを完全一致で照合し、明示的な完了解除と再編集後もポイント値を元へ戻せることを確認した。

実画面は改善前後に各14枚を取得し、両テーマの一覧、選択肢、完了した詳細と配色変更の代表画像を実際に観察した。\
通常と完了の枠を区別でき、数値が薄くならず、段階ごとの色味が残ることを確認した。

## 最終の実機確認

1. ダークとライトで全7値と未見積の Task を表示し、通常と完了の数値を一覧と詳細で読む。
2. 完了した Task にチェック、取り消し線、点線のポイント枠があり、数値が薄くならないことを確認する。
3. 完了を解除してポイントを変更し、再度完了して操作不可へ戻ることを確認する。
4. 白と黒の Project 色、利用者のチャート色とカスタムテーマで、選択行とポイント選択肢も確認する。

VS Code 本体のユーザープロファイルと任意のカスタムテーマは実機操作しておらず、[手動確認](../openspec/manual-checks.md)に1行を追加した。\
全体で35項目の最終実機確認が未確認であり、利用者が行う。\
任意のテーマの前景と背景自体が近い場合まで、今回の152測定から保証するものではない。\
未解決の実装指摘はなく、push、Marketplace 公開、README の画面キャプチャ追加は行っていない。
