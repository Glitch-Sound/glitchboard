# 追加の下書きと保存先の保護

最新の起動と設定案内の集約は [起動改善報告](startup-guidance-report.md) を参照する。

## 修正

Story の名前と行の余白で処理が分かれ、余白では下書きが新しい追加先へ残り、名前では詳細の確認結果より先に下書きを消していた。\
どちらも同じ選択関数へ集め、選択を確定する前に必要な確認を通すようにした。

| 経路と状態 | 結果 |
| --- | --- |
| 名前、余白、別Storyの詳細 | 同じ追加確認を通し、キャンセルでは選択と下書きを維持する |
| Event、Project、左ペイン | ボードの共通入口で同じ追加確認を通す |
| 詳細を編集中 | 詳細の切替確認を先に行い、キャンセルではTask追加欄もそのまま残る |
| 追加先が同じTaskなどの選択 | 確認を増やさず、下書きを同じ追加先で保持する |
| 追加して進む | 入力を始めた元のEventまたはStoryへ追加し、成功後だけ選択を変える |
| 破棄して進む | 明示された入力だけを捨て、保存せず切り替える |
| 追加失敗と保存中 | 元の入力と追加先を保ち、二重送信と移動先の上書きを防ぐ |
| TaskとStoryの片方だけ成功 | 成功した欄だけを閉じ、失敗分の再送で成功済みを二重追加しない |

追加先は入力開始時の修飾IDとして保持する。\
現在表示している Taks か Story かを、送信時に追加先として使い直さない。\
通常の追加と移動前の追加は同じ保存関数を使う。\
共有メッセージ、YAML構造、UUID とコメントは変更していない。

外部更新で追加先そのものが消えた場合や、外部から別Eventが表示された場合の古い追加欄の取消は従来どおりとする。\
下書きの永続保存は追加していない。

## 検証

実 BoardApp の17テストを旧実装で動かし、14件の失敗を確認した。\
残る3件は、行の余白、詳細ボタンと左ペインの経路で既存の詳細確認が先に働く場合であり、元から成功していた。\
修正後は17件すべてと既存テストが成功する。

全体では98ファイル、233テスト、lint、型検査、FSD、ビルド、7 capability の厳格仕様とトレースを確認する。\
実ブラウザーでは両テーマで、余白のポインター操作、名前の選択、詳細確認のキャンセル、実 EACCES と再送を検査した。\
キャンセルと失敗時は YAML の全バイト列が同じであり、追加後も Event 直下の Task 数は変わらず元の Story だけへ追加される。\
別 Event の Story 全体と既存のコメントも維持される。\
実操作の確認を既存の test:ui に含まれる検査へ追加し、プロダクト全体検査のコマンドは変更していない。

## 最終操作確認

[manual-checks.md](../openspec/manual-checks.md) の隔離環境で、新しい管理ファイルを使う。

1. Story 内の Task 追加欄へ名前を入れ、Taks の名前と行左側の余白をそれぞれ選び、キャンセルして同じ欄が残ることを確認する。
2. 同じ状態で Story の詳細を開いて編集し、別レコードへ移る詳細確認をキャンセルして、詳細とTask追加欄の両方が残ることを確認する。
3. 元の追加先へ追加してから進む操作と、明示的な破棄を試し、YAML の保存先を確認する。
4. 別Storyの詳細、Event、Project、左ペインも試し、保存中と失敗後にも追加先が変わらないことを確認する。

実 VS Code の最終 GUI 確認は利用者が行う。\
push、Marketplace 公開、README への画面キャプチャ追加は行っていない。
