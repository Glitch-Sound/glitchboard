# Design

## Context

- 提案：[proposal.md](proposal.md)。
- 対象仕様：[REQ-029](specs/vscode-integration/spec.md#requirement-req-029---管理ファイル未設定時の案内)。
- 制約：[実行境界](../../../tech.md#実行境界)、[配置方針](../../../structure.md#配置方針)に従う。
- 影響する境界：Extensionの読込・監視と設定、sharedのメッセージ検証、両Webviewの案内UIである。

現行の`extension.ts`は設定値が空の場合だけ`unconfigured`を送信する。
`BoardSession.reload()`は読込エラーを文字列へ変換し、直前の状態を保って配信する。
`ManageSetup.tsx`には二つの`button`があるが専用CSSがなく、Tailwindの初期化後にボタンの外観を明示する必要がある。
`setupManage()`にはファイルダイアログ、`wx`による新規作成、設定更新、取消時の無変更が既にある。

## Goals / Non-Goals

**Goals:**

- REQ-029の不在状態を文字列解析によらず判定し、両画面に同じ状態を配信する。
- 読込済みデータを保持したまま復旧操作へ進め、通常の読込エラーと区別する。
- 作成・選択を両テーマで明確なボタンとして示す。

**Non-Goals:**

- YAML形式、計算、Projectの読込範囲、保存範囲、Git連携の変更。
  管理ファイルへの接続復旧が目的である。
- 全画面のボタン部品の刷新。
  共通の案内だけに装飾を限定する。

## Decisions

### D-01 - 管理ファイルの読込段階で不在を分類する

- 対象：REQ-029-S02、REQ-029-S03、REQ-029-S08、REQ-029-S10。
- 選択：`storage/manage.ts`で管理ファイル自身の`readFile`が`ENOENT`となった場合だけ、パスを持つ識別可能なエラーとして返す。
  `BoardSession.reload()`はそのエラーを不在状態として扱い、他のエラーは従来どおり扱う。
  Projectの読込失敗を同じ不在状態にしない。
- 理由：現行のエラー文字列からは管理ファイル自身とProjectの欠落を確実に区別できないためである。
- 代替案：起動時の存在確認だけでは、利用中の削除と確認後の競合を扱えない。
  `ENOENT`という文字列の検索は対象ファイルを区別できないため採用しない。
- 配置と依存：分類はExtension内に置き、sharedへNodeのエラー型を持ち込まない。
  既存の監視対象を不在中も維持し、復元検知後の成功で不在状態を解除する。
  設定切替後は旧セッションの結果を配信しない現行の判定を維持する。
- データと日付：読込分類はファイルを書き換えない。
  休日、祝日、学習中、複数Projectの計算には影響しない。

### D-02 - 不在状態をスナップショットへ付加する

- 対象：REQ-029-S01、REQ-029-S02、REQ-029-S03、REQ-029-S08、REQ-029-S10。
- 選択：共有スナップショットに任意の`manageAvailability`を追加する。
  値は`{ status: "ready" }`または`{ status: "missing", path: string }`とし、未指定は従来の正常状態として扱う。
  不在時も`projects`、`selectedEventId`、`settings`などの直前の有効な状態を保持する。
  未設定時の`unconfigured`は維持する。
- 理由：`ready`への応答、後から開くWebview、監視による更新で同じスナップショットを使え、既存の状態同期と保全を維持できる。
- 代替案：不在時も`unconfigured`だけを送ると、現在の入口処理がスナップショットを破棄するため採用しない。
  エラーテキストだけで画面を分岐する方式も採用しない。
- 配置と依存：`packages/shared/src/domain/messages.ts`で検証し、`session.ts`の配信型と揃える。
  `board.tsx`と`events.tsx`は検証済みの状態から共通UIを表示する。
  不在時は案内を既存表示の上に追加し、未設定または初回読込失敗でデータがない場合は案内を主表示にする。
  `ManageSetup`へ理由とパスを渡し、長いパスは折り返す。
  状態が正常に戻ったら案内と不在のエラーを消す。
- データと日付：追加するのは通信情報だけである。
  YAMLと設定キーの互換性は変わらない。

### D-03 - 案内に限定したボタンの外観と操作を定義する

- 対象：REQ-029-S01、REQ-029-S02、REQ-029-S09。
- 選択：既存ラベルとネイティブの`button type="button"`を維持し、専用クラスで背景、枠、内側の余白、ボタン間の間隔、カーソル、ホバー、`focus-visible`を定義する。
  新規作成には`--vscode-button-*`、選択には`--vscode-button-secondary*`、フォーカスには`--vscode-focusBorder`を使う。
  狭いサイドバーでは縦に並べるか折り返し、ラベルやパスが横へはみ出さないようにする。
- 理由：HTML上のボタンであることに加え、見た目でも操作を判別できる必要がある。
  ネイティブ要素によりTab、Enter、Spaceの標準動作を使える。
- 代替案：テキストリンクやアイコンだけの表示では利用者の指定を満たさない。
  全`button`へのグローバル装飾は既存のタイムラインやツールバーへ波及するため採用しない。
- 配置と依存：`ManageSetup.tsx`と`app/style.css`に限定し、両入口で再利用する。
  新しいライブラリと外部通信は不要である。
- データと日付：表示だけを変更し、データ保存と計算には影響しない。

### D-04 - 既存の設定操作を復旧にも使う

- 対象：REQ-029-S04、REQ-029-S05、REQ-029-S06、REQ-029-S07。
- 選択：既存の`chooseManage`と`createManage`を共有スキーマで検証し、VS Codeの開く・保存ダイアログへ接続する。
  作成時の初期データ、`wx`、設定のWorkspaceまたはGlobalへの保存、取消時の無変更を維持する。
  同じ設定パスへの新規作成でも、監視または再読込により両画面が復帰することを保証する。
  失敗は既存の`operationResult`で返して上部に示し、案内を維持する。
- 理由：管理ファイル不在でも初期設定と同じ操作で復旧でき、独立した作成経路を増やす必要がない。
- 代替案：不在の設定先へ自動作成する方式は、保存先を利用者が選ぶ現行手順と依頼の選択操作に合わない。
- 配置と依存：`extension.ts`の`setupManage()`、`operations.ts`、両入口と共通案内を利用する。
  正常スナップショットの受信時には復旧前の操作エラーを残さない。
- データと日付：既存YAMLの上書きとコメントの変更は行わない。
  新規ファイルのみ現行の初期値を保存する。

## Verification Plan

- 正常、境界、異常：各テスト名にREQ-029とシナリオIDを記載する。
  実ファイルとVS Code APIのモックを組み合わせ、S02・S03・S08・S10の失敗を確認してから状態処理を実装する。
  S01・S04〜S07・S09は両入口のUIと設定操作を検証する。
  管理ファイル自身の欠落とProject欠落を別々に作り、権限エラーはOS差に依存しないモックで再現する。
- 回帰：既存の`req-013-s02.test.ts`、`req-013-s03.test.ts`、`req-013-s01-snapshot-validation.test.ts`、`req-014-setup-schema.test.ts`、`regression-webview.test.ts`を実行する。
  S01の表示条件を不在へ拡張する理由は利用者の依頼であり、既存の未設定案内と操作メッセージは維持する。
- 非機能要件：新規採番は不要である。
  テーマ変数とローカル処理を維持し、既存のNREQ-003とNREQ-001へ回帰影響がないことを確認する。
- 画面確認：Playwrightで通信を差し替え、ボードと幅240pxのEVENT一覧をダーク・ライト両テーマで描画する。
  通常、ホバー、キーボードフォーカス、長いパス、Enter・Spaceの送信、横はみ出しを確認し、画像を`artifacts/manage-setup/`へ保存する。
  既存の専用Playwright設定がないため、この対象に絞った起動手順を実装時に整える。
- 手動確認：VS Code安定版で不在の設定先を開き、両ボタンから実ダイアログを操作する。
  取消、作成、選択、利用中の削除と復元を確認し、両テーマの画像と結果を台帳へ記録する。
- 全体検証：`corepack pnpm test`、`corepack pnpm typecheck`、`corepack pnpm check`、`corepack pnpm check:fsd`、`corepack pnpm build`、`openspec validate add-missing-manage-file-actions --strict`、`git diff --check`を実行する。
  成功と未実施を区別して台帳へ記録する。

## Risks / Trade-offs

| 対象IDまたは設計節 | リスクや制約 | 対処と検証 |
| --- | --- | --- |
| D-01 | Project欠落の誤分類 | 管理ファイルの読込箇所だけで分類、S08 |
| D-02 | 不在通知で直前データを消す | スナップショットを保持、S03 |
| D-02 | 古い設定先の非同期通知 | 現行セッション判定を維持、設定切替テスト |
| D-03 | サイドバーと長いパスのはみ出し | 折り返しと両テーマの画面確認、S09 |
| D-04 | 同じ設定値への作成で更新が起きない | 作成監視・再読込で復帰、S05 |

## Migration Plan

データ移行は不要である。
共有メッセージの任意項目は旧形式のテストデータも受け入れる。
READMEの初回手順に、不在時も両ボタンから接続を直せることを追記する。
問題が起きた場合は今回のコードとUIを戻せば現行動作へ戻り、利用者のYAMLと設定の移行は不要である。

## Open Questions

なし。
ボタン名、保存先選択、初期データ、設定保存範囲、取消と排他的作成は既存の動作を維持する。
