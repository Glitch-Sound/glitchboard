# hierarchy-editing Specification

## Purpose

階層の追加・変更・削除は、個人が複数Projectの作業をVS Codeで管理する際に、管理項目を少ない操作で追加・更新・削除し、計算結果へ即時反映する。\
この機能は管理対象の状態と画面の振る舞いを一貫して扱う。

## Requirements

### Requirement: REQ-022 - インライン追加

WHEN 各階層の見出し右端の枠線の追加ボタンを選んだとき、GlitchBoard はその場で入力し、Enter で検証と保存、Esc で取消を行わなければならない(SHALL)。\
Project は名前と未使用色、Event は名前、Project、期限、Story と Task は名前を入力する。\
Event の初期 Project は選択中 Event と同じ、Task は未見積とする。\
保存成功後だけ欄を閉じ、失敗時は入力を残す。\
EVENT 一覧の欄は見出し直下に置き、名前欄に「Event名」を示す。\
期限は直接入力または Webview 内の月移動可能なカレンダーで選べ、native API 不在、例外時も両レイアウトで使える。\
日付選択だけでは送信せず、カレンダー中の Esc はカレンダーだけを閉じ、全入力を保持する。\
期限が未入力または実在しない日なら送信しない。

#### Scenario: REQ-022-S01 - Event追加

- **GIVEN** Event見出しで選択中Projectがある。
- **WHEN** 名前と期限を入力してEnterを押す。
- **THEN** そのProjectにEventが追加される。

#### Scenario: REQ-022-S02 - 取消

- **GIVEN** Storyの入力欄が開いている。
- **WHEN** Escを押す。
- **THEN** Storyは追加されず入力欄が閉じる。

#### Scenario: REQ-022-S03 - 保存失敗

- **GIVEN** 追加の入力欄に名前を入力した。
- **WHEN** 保存に失敗する。
- **THEN** 入力欄を開いたまま入力値を残し、画面上部に失敗理由を表示する。

#### Scenario: REQ-022-S04 - Project色の初期値

- **GIVEN** 既存Projectが青、紫、緑を使用している。
- **WHEN** Projectの追加欄を開く。
- **THEN** 既存Projectが使用していない色が初期選択される。

#### Scenario: REQ-022-S05 - DatePickerからEventを追加

- **GIVEN** 名前とProjectを指定したEvent追加欄が開き、`showPicker()`が存在しないか`SecurityError`を投げる環境である。
- **WHEN** 「期限を選ぶ」を押す。
- **THEN** Webview内に「期限のカレンダー」を表示し、日付を選べる。
- **AND** 日付を選ぶと期限へ反映し、カレンダーを閉じる。
- **AND** 日付を選んだだけでは追加要求を送らず、その後の追加確定で選んだ`YYYY-MM-DD`と名前とProjectを保存する。
- **AND** `embedded`と`popover`のどちらでも同じ結果となる。

#### Scenario: REQ-022-S06 - カレンダーの操作と取消

- **GIVEN** 名前、Project、期限を入力済みのEvent追加欄からカレンダーを開いている。
- **WHEN** Escを押すかカレンダーの枠外をクリックする。
- **THEN** カレンダーだけが閉じ、追加欄と各入力値を維持する。
- **AND** Escで閉じた場合は期限の選択操作へフォーカスが戻る。
- **AND** 期限ボタンはTabで移動してEnterまたはSpaceで開け、日付は矢印で移動してEnterまたはSpaceで選べる。
- **AND** カレンダーの操作キーだけではEventを追加しない。

#### Scenario: REQ-022-S07 - 期限の未入力と不正日付

- **GIVEN** Event名とProjectは入力済みで、期限は未入力、または直接入力した`2026-02-30`である。
- **WHEN** 追加を確定しようとする。
- **THEN** 保存要求を送らず、追加欄と名前とProjectを保持する。
- **AND** 未入力の場合はカレンダーを開いて期限の選択を案内する。
- **AND** 不正日付の場合は期限欄に理由を示し、直接修正またはカレンダーでの選択により追加を再操作できる。

#### Scenario: REQ-022-S08 - 月移動と暦日の保持

- **GIVEN** 選択済みの期限がある場合はその月、未入力の場合は日本時間の当月をカレンダーで表示する。
- **WHEN** 前月・翌月の操作で目的の月へ移動して日付を選ぶ。
- **THEN** `2026-12-31`から翌月の`2027-01-01`を選べ、`2028-02-29`も選べる。
- **AND** 保存要求の日付は選んだ暦日と一致し、端末のタイムゾーンによって前日または翌日へ変わらない。
- **AND** 過去日、休日、日本の祝日も選択できる。
- **AND** 有効な日付を`YYYY-MM-DD`で直接入力した場合も同じ日付を保存できる。

#### Scenario: REQ-022-S09 - 両テーマと狭い表示面

- **GIVEN** ダークまたはライトテーマで、幅240pxのEVENT一覧、または通常レイアウトのEvent追加欄を表示している。
- **WHEN** 期限のカレンダーを開く。
- **THEN** 月、曜日、日付、選択中の日付、フォーカスを判別できる。
- **AND** スクロール領域やフォームの枠で切れず、月移動と日付選択を操作できる。
- **AND** カレンダー表示によって画面外へ操作対象がはみ出さない。

### Requirement: REQ-023 - ポイント変更

WHEN Taskのポイントバッジを選んだとき、GlitchBoardは SHALL 1、2、3、5、8、13、21の7値からスライダーまたは数値で選択させ、保存後に集計と危険を再計算する。\
1と2は青、3と5は緑、8と13はオレンジ、21は赤紫で表示する。
ポイントの選択肢はEscまたは枠外のクリックで閉じる。
選択肢はカードに現在値、スライダー、色付きの7値を横一列、未見積を別行の順で示す。

#### Scenario: REQ-023-S01 - 未見積を設定

- **GIVEN** 未見積Taskがある。
- **WHEN** ポイントバッジから8を選ぶ。
- **THEN** 8ptのオレンジ色になり残りポイントと予測が更新される。

#### Scenario: REQ-023-S02 - 選択肢を閉じる

- **GIVEN** ポイントの選択肢が開いている。
- **WHEN** Escを押すか枠外をクリックする。
- **THEN** ポイントを変えずに選択肢が閉じる。

### Requirement: REQ-024 - 完了の切り替え

WHEN Taskのチェックを切り替えたとき、GlitchBoardは SHALL 完了時に日本時間の当日をdoneAtへ記録し、解除時にdoneAtを削除し、全集計を更新する。

#### Scenario: REQ-024-S01 - 完了と解除

- **GIVEN** 2026-11-03に未完了Taskがある。
- **WHEN** Taskをチェックする。
- **THEN** doneAtが2026-11-03となり残りポイントから外れる。

#### Scenario: REQ-024-S02 - 完了解除

- **GIVEN** 完了済みTaskがある。
- **WHEN** チェックを外す。
- **THEN** doneAtが消え残りポイントへ戻る。

### Requirement: REQ-025 - 確認付き物理削除

WHEN Project、Event、Story、Taskの削除を選んだとき、GlitchBoardは SHALL 子孫の種類別件数を示して確認を求め、承認時だけ対象と全子孫をYAMLから物理削除する。
保存または削除に失敗した場合は、拡張側から返された理由を画面上部に表示する。
確認は画面中央のダイアログに日本語の種類名と名前、0件を除いた子孫件数、赤い削除ボタンを示す。
ダイアログは背景と枠を持つカードとし、警告アイコン、削除対象、同時に消える件数、「元に戻せません」、取消と削除のボタンを示す。

#### Scenario: REQ-025-S01 - 子孫の確認

- **GIVEN** StoryにTaskが12件ある。
- **WHEN** 右クリックから削除を選ぶ。
- **THEN** Task 12件も削除される確認が出る。

#### Scenario: REQ-025-S02 - 取消

- **GIVEN** 削除確認が表示されている。
- **WHEN** 取消を選ぶ。
- **THEN** YAMLが変更されない。

#### Scenario: REQ-025-S03 - 削除失敗

- **GIVEN** 表示後に保存内容が更新され、削除要求が拒否される。
- **WHEN** 削除を確定する。
- **THEN** 画面上部に失敗理由を表示する。

### Requirement: REQ-033 - Story 作成なしの Task 追加
WHEN Event の Task 追加を保存したとき、GlitchBoard は Story の事前作成を要求せず、未見積の Task を Event 直下へ保存しなければならない(SHALL)。\
通常 Story 内の Task と同じ属性と操作を持ち、自動で Story を作ってはならない。\
直接追加と Story 向け追加の保存先を明確に分ける。\
空白の名前、不正な追加先、保存失敗では保存済みデータを変えてはならない。\
Story 一覧の見出しは Story、直接 Task の仮想グループ名は正確に Taks とし、自動 Story は保存しない。

#### Scenario: REQ-033-S01 - 最初の Task

- **GIVEN** Story がない Event がある。
- **WHEN** Event の Task に「調査」を追加する。
- **THEN** 未見積の「調査」1件が保存され、再読込後も Task として表示される。

#### Scenario: REQ-033-S02 - 繰り返し追加と保存先

- **GIVEN** 通常 Story に Task がある。
- **WHEN** Event の Task に2件を続けて追加する。
- **THEN** 通常 Story とその Task はそのままで、Event 直下に新しい Task 2件だけが保存される。

#### Scenario: REQ-033-S03 - 不正な追加と失敗

- **GIVEN** 保存済みの Event がある。
- **WHEN** 下表の追加を試みる。
- **THEN** 保存済みデータは変わらず、理由を返す。

| 条件 |
| --- |
| 空白だけの名前 |
| 存在しない Event |
| 保存先が書き込めない |

#### Scenario: REQ-033-S04 - 未入力と取消

- **GIVEN** 空の Event で Task 追加欄を開いている。
- **WHEN** 空白だけで保存するか Esc で取り消す。
- **THEN** 追加要求は送らず、取消後に再び開くと入力欄は空である。

#### Scenario: REQ-033-S05 - 直接 Task の仮想グループ名

- **GIVEN** Event に直接 Task がある。
- **WHEN** 下部の Story 一覧を表示する。
- **THEN** 見出しは Story、仮想グループは Taks であり、Project YAML に Story は自動生成されない。

### Requirement: REQ-034 - 更新中の選択と入力維持

WHILE 同じ Event を表示している間、GlitchBoard はデータ更新後も存在する Story 選択と未保存の追加入力を維持しなければならない(SHALL)。\
IF 選択中の Story が消えた場合、THEN 追加入力を取り消し、有効な選択へ戻さなければならない(SHALL)。\
保存失敗では入力を残して再送でき、保存中の重複送信を防がなければならない(SHALL)。

#### Scenario: REQ-034-S01 - 更新で選択と入力を保持

- **GIVEN** 2番目の Story を選び、Task 追加欄に「下書き」を入力した。
- **WHEN** 同じ Event の Task 完了状態が更新される。
- **THEN** 2番目の Story が選択されたままで「下書き」も残る。

#### Scenario: REQ-034-S02 - 選択先消失と Event 切替

- **GIVEN** 追加欄に未保存の名前を入力している。
- **WHEN** 選択 Story が削除されるか別の Event に切り替わる。
- **THEN** 古い追加欄は閉じ、別の追加先へ入力を引き継がない。

#### Scenario: REQ-034-S03 - 失敗後に再送

- **GIVEN** Task を入力し、保存が失敗した。
- **WHEN** 同じ入力を再度保存する。
- **THEN** 同じ追加先と名前を送信し、成功した後だけ欄を閉じる。

#### Scenario: REQ-034-S04 - 二重送信と取消後の応答

- **GIVEN** Task の保存要求を送って応答を待っている。
- **WHEN** 再度保存を試すか、取消後に再び追加欄を開いてから前の応答を受ける。
- **THEN** 保存要求は1件で、前の応答が新しい入力欄を消さない。
